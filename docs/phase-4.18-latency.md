# Phase 4.18 — Окно ваншота: сеть вон из горячего пути + визуальный слой аддона

> 2026-07-30. Требование Влада (дословно): «26 секунд не критично, а я говорю, что
> и за 2 секунды можно ваншотнуться и проиграть». То есть цель — **доли секунды**,
> а не «быстрее, чем было».

## 1. Корень 26 секунд: сеть стояла ВНУТРИ цикла чтения лога

Что было измерено 30.07 (память проекта: `measured-26s-blind-window`,
`root-cause-26s-inline-post`):

- клиент пишет combat-лог **realtime** (mtime файла и последняя строка расходятся
  на 2 мс) — гипотеза «клиент буферизует» опровергнута, данные на диске сразу;
- ворота открылись в 13:49:45.260, первая «Сессия начата» у моста — 13:50:11:
  **блиндовое окно 26 секунд**, при том что враг проявился в логе через 0.04с.

Механизм: `await client.send(payload)` стоял **внутри** `async for raw_line in
tailer.lines()`, а бэкенд перед ответом на `/v1/events` ходил в Discord REST.
Каждое событие блокировало чтение лога на 0.3–1.5с (при 500-х с ретраями — до 10с).
Мост форвардит до 90 кастов/мин — отставание копилось и не рассасывалось.

### Что сделано

| Звено | Было | Стало |
|---|---|---|
| `/v1/events` → Discord DM | `await` внутри обработки запроса | `ctx.spawn_dm()` — фон, порядок DM сохранён цепочкой на игрока |
| `/v1/events` → постматч (LLM Sonnet) | `await` внутри обработки ARENA_END | весь разбор в `ctx.spawn_bg()` |
| мост: чтение ↔ отправка | один цикл | `EventSender` + `asyncio.Queue` (drop-**oldest**), воркер отдельно |
| мост: ретраи POST | `[1, 2, 5, 10]` ≈ 18с | `[0.3, 0.7]`, таймаут 10с → 4с |
| диагностика | её не было (дважды гадали) | лог «время в логе ↔ wall-clock», латентность POST, счётчики `SendStats`, warning на обработку `/v1/events` дольше 150 мс |

Почему drop-**oldest**, а не drop-newest: просроченная подсказка в арене не просто
бесполезна — она вредна («кик!» после того, как каст прошёл). По той же причине
событие, пролежавшее в очереди дольше 5с, не отправляется вовсе.

**Статус «sent» теперь означает «принято к доставке», а не «Discord подтвердил».**
Ждать подтверждения некому: мост в этот момент обязан читать лог.

## 2. Дефект хуже задержки: советы шли под ЧУЖОЙ класс

`our_comp=hunter, player_class=HUNTER` — а Влад играл **рогой**. Отсюда же лишние
токены: `our_comp` входит в ключ кэша разборов, при неверном составе кэш не
срабатывает и один и тот же сетап генерится заново.

Причина: в строку `allies` попадали **только юниты с известным классом**, а класс
роги за 26 секунд ворот не раскрылся. Первым в списке оказался напарник-хант, а
бэкенд берёт `player_class = allies[0]`.

Починено четырьмя независимыми правками:

1. **Долгая память классов.** Класс персонажа не меняется никогда, класс ника —
   тоже. `_self_class` и `_known_classes` живут весь запуск моста и заполняются с
   ЛЮБОГО каста, включая баффы в городе до очереди. Ростер матча по-прежнему
   собирается заново — память лишь подставляет классы известным никам.
2. **Слот игрока есть всегда.** Если класс всё же неизвестен, мост шлёт явный
   `UNKNOWN/UNKNOWN` первой позицией, и бэкенд получает «класс неизвестен» вместо
   уверенно неверного. `our_comp` при этом собирается из того, что известно.
3. **Класс по ИМЕНИ спелла** как фолбэк к таблице id. Живой промах: враг скастовал
   `Arcane Intellect` id 1459, а в таблице лежал только ранг 27126. У баффов по 5–7
   рангов, добивать id — бесконечная гонка; имя у всех рангов одно. Ограничение:
   английский клиент (лог локализован), поэтому имя — именно фолбэк.
4. **Ростер команды — строго по ауре Arena Preparation.** Раньше любой friendly,
   что-либо скастовавший, попадал в союзники: в живом логе после матча туда влетели
   десятки имён из открытого мира, а `bracket` считается по их числу.
   Плюс дедуп `ARENA_START` теперь учитывает и наш состав — раньше позднее
   раскрытие напарника до бэкенда не доезжало вовсе и `our_comp` фризился.

## 3. Почему одного ускорения мало: визуальный слой аддона

Бюджет по звеньям (память: `latency-budget`) даёт **~1.5–2с даже на идеальном
пути**: мост → POST (~0.1–0.3с) + поллинг `/v1/hints` (в среднем 0.25с) + старт
`say` (~0.1–0.3с) + сама фраза (0.7–3.2с). Это не «плохая реализация», это число
звеньев. В окно ваншота такая цепочка не попадает в принципе.

Поэтому решение, которое обязано быть мгновенным, принимается **в клиенте и
показывается ГЛАЗАМИ**:

- `UnitClass("arena1")` отдаёт классы врагов **в момент ворот** — без кастов, без
  combat-лога, без сети (то самое 26-секундное окно закрывается нулём);
- KB скомпилирована в `addon/ArenaCoach/KillTargets.lua` генератором
  `tools/gen_addon_killtargets.py` (78 матчапов; ключ
  `<bracket>|<наши классы>|<классы врагов>`);
- незнакомый сетап — фолбэк-эвристика, порт `killpriority.py`, помечается «≈»;
- тринкеты аддон трекает своим CLEU и показывает «БЕЗ ТРИНКЕТА»;
- **дубли класса** (две роги) аддон разрешает лучше сервера: он видит HP и то, кто
  уже потратил тринкет. Цель — та, что тринкетнула;
- вывод: череп (raid-target) + панель «АРЕНА N / КЛАСС / БЕЗ ТРИНКЕТА».

Череп лучше речи: виден на фрейме и нейтплейте, виден напарнику и не тратит бюджет
речи (Phase 4.17). Голос остаётся тому, что терпит секунду: старт, окна КД, постматч.

**⚠️ Проверить в живой игре:** метку в 2.4.3 ставит лидер/ассист пати, и имя API
между сборками отличается. Вызов защищён `pcall` и пробует `SetRaidTarget` →
`SetRaidTargetIcon`; если не сработает, панель аддона всё равно всё показывает.

Логика аддона проверяется тестами без клиента: `tests/test_addon_overlay.py`
гоняет реальные .lua в lua5.1 поверх заглушки клиентского API.
